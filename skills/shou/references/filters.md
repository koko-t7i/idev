# 取舍规则

两道硬门槛加一层裁量。门槛的字段按调研类型和候选类型取值，都要有来源页面。每个候选都要在 `candidates.jsonl` 里落一个 `verdict`。被剔除的留痕，但不进产出、不在正文点名。

## 时间基准

取数开始时确定 `CUTOFF`，即当前日期回溯 12 个月，写进 `plan.md`。当前为 2026-09-21 时，`CUTOFF` 是 2025-09-21。后续所有时效判定都用这个值，中途不重算。

# 类型 A：现成方案盘点

候选是具体的仓库、产品、服务。

## 候选类型

| kind | 指什么 |
|---|---|
| `repo` | 开源仓库 |
| `product` | 闭源产品、SaaS、商业服务、托管 API |
| `article` | 文章、报告、榜单 |

同一个东西既有开源仓库又有商业版时，按用户这次调研的关注点选一种登记，不要重复两行。

## 门槛一：热度

| kind | 要求 |
|---|---|
| `repo` | star 大于 50 |
| `product` | 至少一条带数字和来源链接的采用度证据 |
| `article` | 不要求 |

`product` 可接受的采用度证据，任选其一：

- 第三方评测平台的评价条数或排名，例如 G2、Capterra、ProductHunt。
- 公开的用户数、客户数、付费客户数。
- 公开的融资额、估值或员工规模。
- 应用商店的评分人数或下载量。
- 可数的媒体报道或分析师报告数量。
- 社区规模，例如官方社区成员数、讨论区活跃帖数。

不接受的：官方文案里没有数字的形容词（"领先的"、"广泛使用的"）、估算值、同行口碑的转述。

`product` 不设统一的数值门槛，因为各类指标不可比。硬性要求是这个数字存在且能点开来源。数字大小进入关联性裁量，明显边缘的按 `drop:irrelevant` 剔除。

## 门槛二：时效

`last_active` 早于 `CUTOFF` 的剔除。各类型取自：

| kind | 取哪个日期 |
|---|---|
| `repo` | 最后一次提交或发版 |
| `product` | 最近一次 changelog、发版公告、官方博客。都没有则取最近一篇第三方报道 |
| `article` | 发布日期 |

超过一年没有更新的仓库、产品或文章属于过时信息，热度再高也照样剔除，不因为"经典"或"知名"破例。这类东西如果对理解全局确有必要，只能在取舍要点里用一句话提及，不占表格行。

## verdict

| verdict | 含义 |
|---|---|
| `keep` | 两道门槛都过，且与需求相关 |
| `drop:traction` | 热度不达标，或采用度证据缺失、拿不到数字 |
| `drop:stale` | `last_active` 早于 `CUTOFF`，或读不到活跃日期 |
| `drop:irrelevant` | 门槛过了但与需求无关 |

## 缺数据的处理

| 情况 | 处理 |
|---|---|
| 热度字段读不到 | 再核实一次，仍读不到则剔除，记 `drop:traction` |
| `last_active` 读不到 | 同上，记 `drop:stale` |
| 页面无法访问 | 剔除，计入信息缺口的计数 |

闭源产品经常查不到具体日期，这种情况如实剔除并计入缺口，不要用"持续更新中"这类措辞代替日期。

## 行数

保留 8 到 25 行。少于 8 行说明覆盖不足，补检索角度再来一轮。多于 25 行说明取舍不够，按关联性和热度收紧。

# 类型 B：实现方案

候选是机制、算法、模式这一层。star 和热度在这里不适用。

## 候选的粒度

一个候选等于一个可命名、可单独取舍的机制。例如限流的候选是固定窗口、滑动窗口日志、滑动窗口计数、漏桶、令牌桶、并发信号量、集中式配额服务这一层，不是"某个限流库"。

粒度判断：两个候选如果在同样的约束下会做出不同的取舍，就是两条；如果只是同一机制的不同实现，合并成一条，把实现留给"典型实现"字段。

## 门槛一：生产采用证据

每个方案至少要有一条可核实的证据，说明它在生产中被使用，或被权威文档推荐，带链接。可接受的：

- 主流实现的官方文档或源码位置，例如网关、数据库、标准库里的对应机制。
- 公司工程博客、事故复盘、架构文章里的实际使用记录。
- 标准或规范，例如 RFC、协议文档。
- 论文加上至少一个落地实现。

不接受的：只在教程、面试题、内容农场文章里出现的方案；只有概念描述没有任何实现或使用记录的方案。

## 门槛二：证据时效

方案本身不按时间剔除。时效作用在证据上：至少一条证据在 `CUTOFF` 之后，说明它当前仍在使用或仍被讨论。

只有多年前的文献支撑、近一年找不到任何使用或讨论记录的方案，记 `drop:legacy`。如果它是其他方案的基础概念，在取舍要点里用一句话交代，不占表格行。

## 门槛三：适用条件写得出来

写不出"在什么条件下应该选它"和"在什么条件下不该选"，记 `drop:unclear`，回去补证据或剔除。这一条用来挡只有名字、没有使用条件的候选。

## verdict

| verdict | 含义 |
|---|---|
| `keep` | 三道门槛都过，且与需求相关 |
| `drop:unproven` | 找不到生产采用证据 |
| `drop:legacy` | 近一年无任何使用或讨论记录 |
| `drop:unclear` | 说不清适用条件 |
| `drop:irrelevant` | 门槛过了但与本次需求的约束无关 |

## 关联性在类型 B 的含义

对照复述里的约束那一句：技术栈、规模量级、已有基础设施、部署形态。明显不符合约束的方案剔除，例如单机进程内方案用在多实例部署上、需要专门协调服务而团队没有这套基础设施。

## 行数

保留 4 到 12 行。方案数量少于产品，行数偏多时先检查是不是把同一机制的多个实现拆成了多行。少于 4 行说明机制族没找全，补检索角度再来一轮。

# 两种类型共用的裁量规则

门槛之外的取舍由 agent 判断，依据是 `plan.md` 第一节的复述全文。剔除时记 `drop:irrelevant`。

判断时对照复述里的用途那一句，不是只对照关键词。常见该剔除的情况：

- 名字或标签命中，实际解决的问题不同。
- 属于用户明确排除的范围。
- 同一团队的多个变体，或同一机制的多个实现，只留一条。
- 镜像、fork、教程合集、榜单索引本身。它们是发现渠道，不是被调研对象。
- 处于长尾且同组已有更有代表性的同类。

## 剔除情况的呈现

产出里只写一句汇总：`共评估 N 个候选，剔除 M 个。` 不逐个列出被剔除的项目。
