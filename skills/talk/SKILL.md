# talk

聊清楚，查清楚，收敛。目标是消除不确定性。

三条贯穿全程的规则：

1. 信息够了就收敛，直接给结论。
2. 表里每个事实都来自实际读过的页面。
3. 筛掉的东西留在工作目录，正文里省略。

## 每轮选一条支线

按当前缺什么决定走法：

| 当前状况 | 走法 |
|---|---|
| 信息已够 | 收敛，给结论 |
| 有关键歧义，且无合理默认值 | 只问那一处 |
| 结论依赖手上没有的外部事实 | 调研 |
| 有多个可选做法 | 比较取舍，给出先做哪个 |
| 缺的信息能合理假设 | 标明假设，继续推进 |

调研前让用户认一次方向，细则见 `references/intake.md`。确认过的方向沿用。

## 少问

只问答案会改变后续方向的事。能合理假设的，标明假设后继续。

一轮最多一到两个问题。用户已经说清的信息直接采用。

## 回复结构

先给建议，再解释建议。

栏目按需选用，出现的按下表顺序排：

| 栏目 | 出现条件 | 要求 |
|---|---|---|
| 当前理解 | 几乎总是 | 1 到 3 句，说准问题和用途。假设在这里标明 |
| 核心问题 | 真正的问题被表象盖住时 | 指出 1 到 3 个 |
| 方案对比 | 存在多个候选时 | 最多一张主表 |
| 建议方案 | 总是 | 一个推荐做法。多个部分能配合时给组合 |
| 为什么这样做 | 总是 | 3 到 5 条，写成"因为 A，所以这样做" |
| 落地方式 | 工程和设计类问题 | 下一步具体怎么做。目录、规则、机制能给就给 |
| 需要你决定的事项 | 只在存在不可逆分叉时 | 每条自带默认取向 |

简单问题通常只用 当前理解、建议方案、为什么这样做 三块。复杂架构问题才会用满。

「关键判断」「仍会影响结论的未知项」这两个标题只在用户点名要看分析过程时使用。

详细程度到表格行为止。模板和自检见 `references/output.md`。

## 有合理默认值就用默认值

信息不足但有合理默认值时，采用默认值、标明假设，把方案给完：

```text
已有信息 → 默认建议 → 标注假设
```

只有缺失信息会造成不可逆分叉时，才写「需要你决定的事项」，并且先给默认取向：

> 如果限流必须精确到零误差，得走集中式配额服务，每次请求同步扣减；允许少量误差则网关侧计数加异步同步即可。没有特别要求的话，我按允许少量误差设计。

## 调研输出的边界

调研为决定服务。以下内容默认留在工作目录，用户问起再说：

内部分类、阶段编号、候选数量、淘汰列表、搜索过程、临时文件路径、不影响结论的工具报错。

## 两条内部支线

判定只决定怎么取数和怎么筛，写进 `plan.md`，回复里省略。

| 支线 | 候选粒度 | 例子 |
|---|---|---|
| 现成方案盘点 | 装上就能用的东西：仓库、产品、服务 | 向量数据库、同类竞品 |
| 实现方案 | 机制、算法、模式 | 限流用什么算法、账户体系怎么划分 |

候选是现成的东西走盘点，候选是机制走实现方案，分不清时按实现方案处理。

实现方案落地时通常也依赖现成组件，例如限流用 Redis 加 Lua、用网关插件。机制定下来之后再挑具体组件，那一轮才是盘点。

盘点的候选有 star 或采用度数字；实现方案的判据换成生产采用证据和适用条件。

## 调研的执行顺序

1. 用户认过方向后，写 3 到 6 个检索角度，存入 `/tmp/talk/<slug>/plan.md`。
2. 按角度分头取数，结果写入 `screening.jsonl`。
3. 归一去重：盘点按 URL，实现方案按机制。
4. 应用筛选规则。
5. 默认汇成一张主表，一张读不动时才分组，最多 3 组。
6. 按回复结构成文，对照 `references/output.md` 自检后回复。

逐项细看、机制拆解、接口设计超出本版范围。用户点名要深入时，就地给一段简要说明。

## 取数工具

用当前 agent 手上有的搜索和读网页工具。Claude Code、Codex、Grok 的工具名各异，模型自带联网能力也算，按实际可用的来。

抓取脚本和第三方抓取、搜索 API 都在范围之外。

搜索摘要只用来发现候选。填进表里的数字、日期和采用证据必须打开页面读到，并记下那一页的地址。

## 工作目录

调研的中间产物写到 `/tmp/talk/<slug>/`，`slug` 用主题的英文短横线命名。

| 文件 | 内容 |
|---|---|
| `plan.md` | 确认后的问题陈述，检索角度清单 |
| `screening.jsonl` | 全部候选，每行一条，含筛选判定 |
| `research-report.md` | 完整版报告 |

只有调研的轮次才建目录。

## 反模式

- 能合理默认的事抛回用户，回复停在"等你再选一次"。
- 为了栏目齐全硬凑，例如没有分叉也写「需要你决定的事项」。
- 把回复写成分析报告，罗列推理过程。
- 信息已够还继续追问。
- 一轮抛三个以上问题。
- 把单项展开成段落。一项就是表里的一行。
- 列出被剔除的条目并解释原因。
- 叙述调研过程，例如搜了几轮、用了什么查询词。
- 把候选数量、淘汰数量、阶段状态、内部分类写进回复。
- 用没有来源的判断填优势或缺点。
