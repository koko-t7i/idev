# talk

调研 skill。先与用户确认调研方向，再做全景扫描，产出筛选、分类、成表的结论。

## 目录

```
talk/
  SKILL.md                    角色、类型路由、分阶段、执行顺序、规则
  references/
    intake.md                 阶段 0：判定类型、确认调研方向
    filters.md                两种类型各自的取舍规则
    landscape.md              阶段 1，类型 A：现成方案盘点
    design.md                 阶段 1，类型 B：实现方案
    output.md                 两套输出模板与交付前自检
```

## 两种调研类型

| 类型 | 问题形态 | 候选是什么 | 例子 |
|---|---|---|---|
| A 现成方案盘点 | 有哪些可以直接用的 | 仓库、产品、服务 | 向量数据库、同类竞品 |
| B 实现方案 | 某个模块用什么方案做 | 机制、算法、模式 | 限流用什么算法、账户体系怎么划分 |

阶段 0 按候选粒度判定：候选是能装上就用的东西走 A，候选是机制走 B，分不清按 B 处理并请用户确认。

两类不是"用现成的还是自己写"的对立。类型 B 的方案落地时通常也用现成组件，方案定下来之后挑组件那一轮才是 A。

## 范围

- 已实现：阶段 0 确认调研方向，阶段 1 全景扫描出表。
- 未实现：阶段 2 及以后的深入单项、机制拆解、落地评估。
- 取数用当前 agent 手上有的搜索和读网页工具，有什么用什么。不写抓取脚本，不接第三方抓取或搜索 API。

## 取舍规则

时间基准统一为当前日期回溯 12 个月，门槛按类型取不同字段。

类型 A：

| 规则 | 说明 |
|---|---|
| 热度（开源） | star 大于 50 |
| 热度（闭源） | 至少一条带数字和来源链接的采用度证据，例如评测平台评价数、公开客户数、融资额、应用商店评分人数 |
| 过时剔除 | 最近活跃早于时效基准日 的仓库、产品或文章剔除，热度高也不破例 |
| 行数 | 保留 8 到 25 行 |

闭源产品的活跃日期取 changelog、发版公告或官方博客，都没有则取最近一篇第三方报道。查不到日期的如实剔除并计入信息缺口。

类型 B：

| 规则 | 说明 |
|---|---|
| 生产采用证据 | 每个方案至少一条可核实的使用记录或权威文档，带链接。教程和面试题不算 |
| 证据时效 | 方案本身不按时间剔除，但至少要有一条 时效基准日之后的证据 |
| 适用条件 | 说不清什么时候该用、什么时候不该用的方案剔除 |
| 行数 | 保留 4 到 12 行 |

关联性裁量两种类型共用：门槛之外由 agent 按确认后的调研请求判断，类型 B 还要对照技术约束。

## 输出约定

类型 A：分类表格，列为项目、热度、最近活跃、优势、缺点，缺点必填，闭源条目在名称后标注，热度写数字加指标名且不做换算。外加 2 到 3 句结论摘要和 3 到 5 条流行趋势。

类型 B：分组方案表，列为方案、机制、适用条件、代价、典型实现，适用条件与代价必填，代价要写具体失效模式。开头给出本次约束下先做哪个和换方案的触发条件，表格之后写 3 到 5 条为什么这么选。

两者都是结论摘要、分类表、为什么这么选三块，分 3 到 4 组，每项一行不展开。结尾最多三行：一行建议，最多一条真会改变结论的待确认项，一行报告路径。
