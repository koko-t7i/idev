# 回复结构、表格模板与自检

一次回复一页读完。先给建议，再解释建议，调研和推理都是为了支撑那个建议。

## 栏目

用得上哪块写哪块，出现的按这个顺序排：

| # | 栏目 | 什么时候出现 | 要求 |
|---|---|---|---|
| 1 | 当前理解 | 几乎总是 | 1 到 3 句，把问题和用途说准。有假设在这里标明，最多 2 条。用户刚确认过就压成半句 |
| 2 | 核心问题 | 真正要解决的问题被表象盖住时 | 1 到 3 个，指出症状背后的成因 |
| 3 | 方案对比 | 确实存在多个候选时 | 最多一张主表 |
| 4 | 建议方案 | 总是 | 直接给推荐做法，需要几件事配合就给组合 |
| 5 | 为什么这样做 | 总是 | 3 到 5 条，每条解释建议 |
| 6 | 落地方式 | 工程和设计类问题 | 下一步具体怎么做，能给目录、规则、机制就直接给 |
| 7 | 需要你决定的事项 | 只有存在不可逆分叉时 | 最多 2 条，每条给出默认取向。没有分叉就整块省掉 |

轻量的问题常常只有 1、4、5 三块，这是正常形态。复杂架构问题才会用到 6 和 7。栏目齐全本身没有价值，凑出来的块要删掉。

默认汇成一张主表。条目多到一张读不动时才分组，最多 3 组，每组至少 2 行，每组一个不超过 20 字的二级标题。

## 表格模板：现成方案盘点

```markdown
| 项目 | 热度 | 最近活跃 | 优势 | 缺点 |
|---|---|---|---|---|
| [owner/repo](url) | 12.3k star | 2026-08-27 | 一句，不超过 25 字 | 一句，不超过 25 字 |
| [某产品](url)（闭源） | G2 340 条评价 | 2026-09-02 | 一句，不超过 25 字 | 一句，不超过 25 字 |
```

| 列 | 要求 |
|---|---|
| 项目 | 名称带链接，指向仓库或主页。闭源的在名称后标 `（闭源）` |
| 热度 | 数字加指标名，让人看出这是什么指标。文章类填 `—` |
| 最近活跃 | `YYYY-MM-DD`，时效判定的依据 |
| 优势 | 必填。写它区别于其他项的地方，不写通用套话 |
| 缺点 | 必填，头部方案也要填。填不出来说明核实不充分，回去补 |

热度列的指标不要求同类可比，开源写 star，闭源写评价数、客户数或融资额都可以，但要带指标名，不写裸数字，也不换算成可比分数。

缺点写可验证的短板：更新频率下降、依赖某家付费服务、只覆盖单一平台、文档缺失、绑定特定运行环境、许可证受限。闭源方案常见的短板是不提供自托管、按坐席收费、接口受限、无法导出数据、路线图不公开。

## 表格模板：实现方案

```markdown
| 方案 | 机制 | 适用条件 | 代价 | 典型实现 |
|---|---|---|---|---|
| 令牌桶 | 一句话，不超过 25 字 | 一句，不超过 25 字 | 一句，不超过 25 字 | [Envoy](url) |
```

| 列 | 要求 |
|---|---|
| 方案 | 领域内通用叫法，不要自造名字 |
| 机制 | 一句话说清它怎么工作。写工作方式，不写好处 |
| 适用条件 | 什么条件下选它。必填 |
| 代价 | 复杂度、资源开销、已知失效模式。必填 |
| 典型实现 | 1 到 2 个带链接的实现或使用记录，链接就是采用证据 |

总列数不超过 6。不排除条件写进"适用条件"的反面或"代价"里，不单独占一列。

代价列写具体条目：需要额外的协调服务、集群下有时钟漂移、突发流量会放大尖峰、内存随 key 数量线性增长、热点 key 打穿单分片。不要写"实现较复杂"这类放到任何方案上都成立的话。

有多个做法时，「建议方案」直接写先做哪个、什么情况下换成另一个。约束不足以选出来时，按最常见的场景取默认值并标明假设。

## 建议方案

给做法，不是给选项。多个部分能配合就写成一套组合，例如"入口文件只放硬规则，领域细则按需加载，可静态判断的移到 CI"，而不是把三件事并列让用户挑。

写到能照着动手的粒度：目录结构、文件划分、规则条目、触发机制，能直接给就给出来。

## 为什么这样做

3 到 5 条，每条解释建议为什么成立，写成"因为 A，所以这样做"。

写这样：

> 文档只能降低规则被忽略的概率，无法强制执行，所以可机器检查的规则应该移进 CI。

不写这样：

> 文档层面的所有手段都只能减缓，不能根治。

差别在于前者落到"所以这样做"，后者停在"我推出了什么"。有主表时，每条要能指回表里至少 2 行。

## 不重复

一个事实在回复里只出现一次。写进表格的，判断里不再复述；某条限制对多行都成立，写进分组标题下那一句，不在每行重写。表格读得出来的信息不算判断。

## 需要你决定的事项

先判断这个缺口值不值得占一块：

| 情况 | 怎么处理 |
|---|---|
| 存在合理默认值 | 用默认值，在「当前理解」标明假设，方案照常给完 |
| 两条路都可行，选错了改回来成本低 | 推荐一条，写清什么情况下换 |
| 选错了要推翻已经做出来的东西 | 写进这一块，并给出默认取向 |

这一块最多 2 条，每条写清两边各自意味着什么，末尾给默认：

> 如果这个仓库必须同时兼容 Claude Code、Codex、Cursor，局部规则文件要按三者的共同能力设计；只服务 Codex 则可以用更激进的嵌套规则。没有特别要求的话，我按多工具兼容设计。

把已经说清楚目标的问题再问回去是反模式。用户说"解决 Agent 不遵守约定"，就直接推荐机制并往下做，不要问"你愿意加 CI 校验吗"。

## 一个完整例子

问题是"项目变大之后 Agent 不遵守约定、记忆被稀释怎么办"。用户已经说清目标，所以整轮不反问，直接给方案。

````markdown
## 当前理解

随着项目变大，规范文档会持续增加。真正的问题不是 Agent 找不到文档，而是默认上下文里
规则的权重越来越低，最后出现"读过但不遵守"。

## 核心问题

规则、背景说明、示例、历史设计混在同一套文档里，入口文件又在承担越来越多的索引职责，
于是默认上下文持续膨胀，而所有规则都只能指望模型自觉遵守，没有强制执行的一环。

## 建议方案

分成三层：

1. `AGENTS.md`：只留全局硬规则和规则路由。
2. `docs/rules/`：按领域存放需要按需读取的详细约定。
3. CI / lint：能程序化判断的规则全部移出文档。

```text
AGENTS.md
  - 禁止 api 层直接访问数据库
  - service 不依赖 axum
  - 改 ORM 时读 docs/rules/orm.md
docs/rules/{architecture,api,orm,error}.md
scripts/check_architecture.py
```

## 为什么这样做

- 默认上下文只留高频高优先级的规则，不随文档数量线性增长。
- 领域规则只在相关任务里加载，无关文档不参与竞争注意力。
- 可静态判断的规则交给 CI 之后，遵守与否不再取决于模型是否记得。
- 文档最终只承担机器判断不了的架构语义和设计原则。

## 落地方式

先把现有约定分成三类：永久进入默认上下文、按任务加载、可机器校验。分完再重构
`AGENTS.md`，而不是继续往里追加规则。
````

## 结尾

有报告文件时末尾一行给出路径。用户点名某条要深入时，说明当前只做到清点，就地给一段简要说明。

## 自检

自己过，不把清单和检查结果贴给用户。

| # | 条件 |
|---|---|
| 1 | 出现的栏目按表中顺序排，没有为了齐全而凑的块 |
| 2 | 有「建议方案」和「为什么这样做」，且建议是一个做法，不是一组待选项 |
| 3 | 「为什么这样做」3 到 5 条，每条落到"所以这样做"，有主表时能指回表里至少 2 行，且不复述表里的信息 |
| 4 | 没有用「关键判断」「仍会影响结论的未知项」当标题 |
| 5 | 每个信息缺口要么用了默认值并标明假设，要么确实是不可逆分叉 |
| 6 | 需要用户定的事项不超过 2 条，每条自带默认取向 |
| 7 | 主表一张，分组的话不超过 3 组，每组至少 2 行 |
| 8 | 表里每个事实都有来源页面，且那些页面实际读过 |
| 9 | 正文没有单项的段落式展开 |
| 10 | 回复里没有内部分类、阶段编号、候选数量、淘汰列表、文件路径以外的过程信息 |

调研轮次追加：

| # | 条件 |
|---|---|
| 11 | `/tmp/talk/<slug>/screening.jsonl` 存在，每条都有判定 |
| 12 | 表格行数等于判定为保留的条目数，没有表外补充的项目 |

盘点追加：

| # | 条件 |
|---|---|
| A1 | 判定为保留的条目数在 8 到 20 之间 |
| A2 | 每行热度带指标名，不是裸数字 |
| A3 | 每行最近活跃晚于时效基准日；仓库类 star 大于 50；闭源产品类有带数字的采用度证据 |
| A4 | 闭源条目在项目名后有 `（闭源）` 标记 |
| A5 | 每行的优势和缺点均非空 |

实现方案追加：

| # | 条件 |
|---|---|
| B1 | 判定为保留的条目数在 4 到 12 之间 |
| B2 | 给出了先做哪个，或说明了缺哪个信息才能定 |
| B3 | 每行的适用条件和代价均非空 |
| B4 | 每行有至少 1 个带链接的典型实现或使用记录 |
| B5 | 每个方案至少有一条时效基准日之后的证据 |
| B6 | 代价写的是具体失效模式，不是"实现复杂" |

## 输出禁令

- 不用「关键判断」「仍会影响结论的未知项」当标题，除非用户点名要看分析推理过程。
- 不把能合理默认的信息缺口抛回用户，让回复停在等待回答的状态。
- 不为了保持结构完整而强行输出栏目。
- 不在正文逐项展开成段落，详细程度到表格行为止。
- 不叙述调研过程，包括搜了几轮、用了哪些查询词、派了几个子代理。
- 不告诉用户走的是哪条内部支线，不写阶段编号。
- 不报数量和进度，包括评估了多少、剔除了多少。这些留在 `screening.jsonl` 里。
- 不解释临时目录会被清理这类环境细节。
- 不汇报不影响结论的工具报错。
- 不列出被剔除的条目并解释原因。
- 不输出没有来源支撑的判断。
- 不把不同类型的热度指标混算或换算成可比分数。
- 不在结尾附 `Sources:` 或参考链接列表，链接已经在表格里。
- 不把 `screening.jsonl` 的原始内容贴进回复。
- 不因为方案有名气就省掉它的缺点或代价。
