# 输出模板与自检

回复的目标是一页读完。两种类型共用三块结构：结论摘要、分类表格、为什么这么选。
论证放在表格之后，摘要里只给结果。

---

# 类型 A：现成方案盘点

## 结构

1. 结论摘要，2 到 3 句：这个领域现在的格局，以及按本次用途先看哪几个。
2. 分类表格，3 到 4 组，每组一张表。
3. 流行趋势，3 到 5 条，写表格看不出来的判断。

## 表格模板

每组一个二级标题说明这组是什么，不超过 20 字，然后一张表：

```markdown
### 编排框架

| 项目 | 热度 | 最近活跃 | 优势 | 缺点 |
|---|---|---|---|---|
| [owner/repo](url) | 12.3k star | 2026-08-27 | 一句，不超过 25 字 | 一句，不超过 25 字 |
| [某产品](url)（闭源） | G2 340 条评价 | 2026-09-02 | 一句，不超过 25 字 | 一句，不超过 25 字 |
```

| 列 | 要求 |
|---|---|
| 项目 | 名称带链接，指向仓库或主页。闭源的在名称后标 `（闭源）` |
| 热度 | 数字加指标名，让人看出这是什么指标。文章类填 `—` |
| 最近活跃 | `YYYY-MM-DD`，时效判定的依据 |
| 优势 | 必填。写它区别于同组其他项的地方，不写通用套话 |
| 缺点 | 必填，头部方案也要填。填不出来说明核实不充分，回去补 |

热度列的指标不要求同类可比，开源写 star，闭源写评价数、客户数或融资额都可以，但要带指标名，不写裸数字，也不换算成可比分数。

缺点写可验证的短板：更新频率下降、依赖某家付费服务、只覆盖单一平台、文档缺失、绑定特定运行环境、许可证受限。闭源方案常见的短板是不提供自托管、按坐席收费、接口受限、无法导出数据、路线图不公开。

## 流行趋势

3 到 5 条，每条一句加一行依据。每条要能指回表里至少 2 行，否则是猜测。

---

# 类型 B：实现方案

## 结构

1. 结论摘要，2 到 3 句：本次约束下先做哪个，什么情况下换。只给结果，理由留到第 3 块。
2. 分组方案表，3 到 4 组，每组一张表。
3. 为什么这么选，3 到 5 条：候选之间的权衡，以及选中项在什么条件下不再成立。

摘要不能省。类型 B 要支撑一个决定，方案清单之外还要给出选哪个。约束不足以做出选择时，写清缺哪个信息才能定。

## 表格模板

```markdown
### 令牌类：控制平均速率并允许突发

| 方案 | 机制 | 适用条件 | 代价 | 典型实现 |
|---|---|---|---|---|
| 令牌桶 | 一句话，不超过 25 字 | 一句，不超过 25 字 | 一句，不超过 25 字 | [Envoy](url) |
```

| 列 | 要求 |
|---|---|
| 方案 | 领域内通用叫法，不要自造名字 |
| 机制 | 一句话说清它怎么工作。写工作方式，不写好处 |
| 适用条件 | 什么条件下选它。必填 |
| 代价 | 复杂度、资源开销、已知失效模式。必填 |
| 典型实现 | 1 到 2 个带链接的实现或使用记录，链接就是采用证据 |

不排除条件单独列一列，写进"适用条件"的反面或"代价"里，总列数不超过 6。阶段 0 确认了额外维度时追加，仍不超过 6。

代价列写具体条目：需要额外的协调服务、集群下有时钟漂移、突发流量会放大尖峰、内存随 key 数量线性增长、热点 key 打穿单分片。不要写"实现较复杂"这类放到任何方案上都成立的话。

## 为什么这么选

3 到 5 条，每条一句加一行依据。写方案之间的权衡关系和触发条件，例如"要精确限速就得接受集中式存储的延迟，多数团队在可接受误差下选本地近似"。每条要能指回表里至少 2 个方案。

---

# 不重复

一个事实在回复里只出现一次。写进表格的，要点里不再复述；某条限制对多行都成立，写进分组标题下的一句话，不在每行重写。要点写的是行与行之间的关系，表格读得出来的信息不算要点。

# 结尾

结尾最多三行，按这个顺序：

1. 一行建议：接下来先做什么。
2. 待确认项最多一条，且只写真会改变结论的那条，写明它倒向哪边会换方案。没有就省掉。
3. 一行给出报告文件路径。

用户要求跳过或立即开始时，直接进入阶段 1。

不要在结尾连抛多个问题。信息缺口影响到结论的，并进待确认那条；只影响细节的，不写。用户点名某条要深入时，说明当前只做到清点，就地给一段简要说明。

# 自检

自己过，不把清单和检查结果贴给用户。共用部分，两种类型都查：

| # | 条件 |
|---|---|
| 1 | `/tmp/talk/<slug>/screening.jsonl` 存在，每条都有判定 |
| 2 | 表格行数等于判定为保留的条目数，没有表外补充的项目 |
| 3 | 分组数在 3 到 4 之间，每组至少 2 行 |
| 4 | 表里每个事实都有来源页面，且那些页面实际读过 |
| 5 | 要点 3 到 5 条，每条能指回表里至少 2 行，且不复述表里的信息 |
| 6 | 结尾不超过三行，问题不超过一个 |
| 7 | 正文没有单项的段落式展开 |

类型 A 追加：

| # | 条件 |
|---|---|
| A1 | 判定为保留的条目数在 8 到 20 之间 |
| A2 | 每行热度带指标名，不是裸数字 |
| A3 | 每行最近活跃晚于时效基准日；仓库类 star 大于 50；闭源产品类有带数字的采用度证据 |
| A4 | 闭源条目在项目名后有 `（闭源）` 标记 |
| A5 | 每行的优势和缺点均非空 |

类型 B 追加：

| # | 条件 |
|---|---|
| B1 | 判定为保留的条目数在 4 到 12 之间 |
| B2 | 摘要给出了先做哪个，或说明了缺哪个信息才能定 |
| B3 | 每行的适用条件和代价均非空 |
| B4 | 每行有至少 1 个带链接的典型实现或使用记录 |
| B5 | 每个方案至少有一条时效基准日之后的证据 |
| B6 | 代价写的是具体失效模式，不是"实现复杂" |

# 输出禁令

- 不在正文逐项展开成段落，详细程度到表格行为止。
- 不叙述调研过程，包括搜了几轮、用了哪些查询词、派了几个子代理。
- 不告诉用户这次走的是哪种调研类型，标题和正文都不写类型编号和类型名称。
- 不报数量和进度，包括评估了多少、剔除了多少、阶段几完成。这些留在 `screening.jsonl` 里。
- 不解释临时目录会被清理这类环境细节。
- 不列出被剔除的条目并解释原因。
- 不输出没有来源支撑的判断。
- 不把不同类型的热度指标混算或换算成可比分数。
- 不在结尾附 `Sources:` 或参考链接列表，链接已经在表格里。
- 不把 `screening.jsonl` 的原始内容贴进回复。
- 不因为方案有名气就省掉它的缺点或代价。
