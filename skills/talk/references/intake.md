# 澄清与确认

## 先选支线

| 当前状况 | 做法 |
|---|---|
| 信息够给结论 | 收敛 |
| 有关键歧义 | 只问那一处 |
| 结论依赖手上没有的外部事实 | 确认方向后调研 |
| 缺的信息能合理假设 | 标明假设，继续推进 |

判断标准：这件事不定，结论会不会变。会变但有合理默认值的，取默认值、标明假设。只有"选错了要推翻已做出来的东西"这类不可逆分叉才值得问。

调研前让用户认一次方向。基于已有信息直接收敛的轮次跳过确认。

## 内部支线判定

| 支线 | 候选粒度 | 信号词 |
|---|---|---|
| 现成方案盘点 | 装上就能用的东西 | 有哪些、用什么、选型、竞品、对比、主流方案 |
| 实现方案 | 机制、算法、模式 | 怎么做、什么方案、如何实现、怎么划分、架构 |

"限流有哪些开源库"是盘点，"限流用什么算法"是实现方案。同一主题两边都问得通时看用户要什么：要一份可选清单走盘点，要一组机制和取舍走实现方案。

实现方案的答案里常含现成组件，判定照旧。"限流用 Redis 还是本地计数"问的是机制；定下集中式存储之后再比几个候选组件，那才是盘点。

分不清时按实现方案处理。判定写进 `plan.md`，回复里省略支线名称；需要时问一句用户想要哪种答案。

## 从对话里提取什么

抽不出来的标为假设。

共用：

| 项 | 说明 |
|---|---|
| 对象 | 要盘点什么类别，或要解决什么问题 |
| 边界 | 包含什么，排除什么 |
| 用途 | 支撑什么决定，决定要比较哪些维度 |
| 已知偏好 | 用户已表达的倾向 |

盘点额外提取：

| 项 | 说明 |
|---|---|
| 比较维度 | 热度、最近活跃、优势、缺点之外还需要哪些列 |
| 开源闭源 | 只看开源，只看商业产品，还是都要 |

实现方案额外提取技术约束，它决定哪些方案可选：

| 项 | 说明 |
|---|---|
| 规模量级 | 请求量、用户量、数据量的大致档位 |
| 部署形态 | 单实例、多实例、多地域 |
| 已有基础设施 | Redis、消息队列、网关、服务注册等 |
| 技术栈 | 语言和框架，决定有无成熟实现可参考 |
| 硬性要求 | 必须精确、必须自托管、合规要求等 |

约束问不到就按常见默认值假设，回复里标明。约束全靠推断时方案表会偏，这一项值得多问一句。

## 确认调研方向怎么写

把理解压成 3 到 4 行，每行一句，末尾单独一行问 `我理解得对吗？`。

1. 目标：要盘点什么或要解决什么问题，给什么决定用。
2. 范围：包含什么，排除什么。盘点时说清开源和闭源各取不取。
3. 假设：最多 2 条推断出来的前提。没有就省掉。

筛选门槛是内部规则，产出形态用户已知，两者都省略。

盘点的例子：

> 目标：盘点做 X 的主流方案，用于选型和定位竞品。
> 范围：开源框架和商业产品都要，排除只有演示没有在营的项目。
> 假设：我按服务端方案理解，不含客户端 SDK。
>
> 我理解得对吗？

实现方案的例子：

> 目标：接口限流该怎么做，用来定网关层的实现方式。
> 范围：多实例部署，手上有 Redis，日请求量百万级，允许少量误差。
> 假设：限流粒度按用户和接口两级，不含按租户配额。
>
> 我理解得对吗？

## 什么算确认

用户明确肯定，例如"对"、"可以"、"确认"、"开始"。用户要求跳过确认或立即开始时，直接开工。

同一请求确认一次。后续追加改变了对象或范围时，只重述被改动的那行，再问一次。

## 反模式

- 信息已够还发起确认或追问。
- 复述超过 4 行，或写成分段说明。
- 一次抛出 3 条以上假设。
- 追问用户已经说清的事。
- 复述里夹带搜索结果或初步结论。
- 复述里写内部分类，例如"调研类型：B 实现方案"。
- 用户只补充一个细节，就重写整段复述。

## 写盘

调研的轮次建立 `/tmp/talk/<slug>/plan.md`。开头一行记内部支线。第一节写确认后的问题陈述，它是后续所有取舍的判据。第二节写检索角度清单，格式见 `landscape.md` 或 `design.md`。
