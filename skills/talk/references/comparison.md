# 方案比较

只在候选之间存在真实取舍时比较。先确认比较对象的层级：产品或组件、实现机制、架构位置分别属于不同决策。根据用户约束选择比较维度，不要套固定模板。

## 筛选

1. 收集足以覆盖主要解法的候选，合并同义项和同一机制的不同实现。
2. 排除不满足硬约束的候选。对剩余候选核实会改变排序的事实，取证方式见 [research.md](research.md)。
3. 找出少数值得用户直接比较的选项。相近或明显不合适的选项可以概括，不必逐一列出；若用户要求全景盘点，再扩展覆盖范围。

开源 star、商业采用数字、最近更新日期可以是有用信号，但不能作为所有主题的统一门槛。稳定的成熟方案可能很少更新；新方案也可能没有足够采用数据。评价它们是否适用，应回到本次需求与风险。

## 呈现

先说推荐哪一个，再给决定性取舍和改选条件。仅在并排比较更清楚时使用表格，列只保留本次决策需要的维度。优势、代价和适用条件要具体到当前问题，避免通用形容词。

若问题包含多个独立决策，先给整体建议，再按决策逐个解释。不要让用户同时记住一长串跨层级候选。用户要深入某一项时，就该项展开机制、接口或落地细节；不要以最初的比较范围限制后续讨论。
