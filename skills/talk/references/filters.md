# 取舍规则

硬门槛加一层裁量。门槛字段按支线和候选类型取值，都要有来源页面。每个候选在 `screening.jsonl` 里落一个判定。被剔除的留痕在文件里，正文省略。

## 时间基准

取数开始时确定时效基准日：当前日期回溯 12 个月，写进 `plan.md`。后续所有时效判定都用这个值，中途沿用。

# 现成方案盘点

候选是具体的仓库、产品、服务。

## 候选类型

| 类别 | 指什么 |
|---|---|
| `repo` | 开源仓库 |
| `product` | 闭源产品、SaaS、商业服务、托管 API |
| `article` | 文章、报告、榜单 |

同一个东西既有开源仓库又有商业版时，按本次关注点登记一种。

## 门槛一：热度

| 类别 | 要求 |
|---|---|
| `repo` | star 大于 50 |
| `product` | 至少一条带数字和来源链接的采用度证据 |
| `article` | 免检 |

闭源产品可接受的采用度证据，任选其一：

- 第三方评测平台的评价条数或排名，例如 G2、Capterra、ProductHunt。
- 公开的用户数、客户数、付费客户数。
- 公开的融资额、估值或员工规模。
- 应用商店的评分人数或下载量。
- 可数的媒体报道或分析师报告数量。
- 社区规模，例如官方社区成员数、讨论区活跃帖数。

排除在外的：官方文案里没有数字的形容词（"领先的"、"广泛使用的"）、估算值、同行口碑的转述。

闭源产品各类指标不可比，所以硬性要求只有两条：数字存在，来源能点开。数字大小进入关联性裁量，明显边缘的按 `drop:irrelevant` 剔除。

## 门槛二：时效

活跃日期早于时效基准日的剔除。各类别取自：

| 类别 | 取哪个日期 |
|---|---|
| `repo` | 最后一次提交或发版 |
| `product` | 最近一次 changelog、发版公告、官方博客。都没有则取最近一篇第三方报道 |
| `article` | 发布日期 |

超过一年没更新的仓库、产品或文章属于过时信息，热度再高、名气再大也照剔。对理解全局确有必要的，在取舍要点里用一句话提及。

## 判定取值

| 判定 | 含义 |
|---|---|
| `keep` | 两道门槛都过，且与需求相关 |
| `drop:traction` | 热度不达标，或采用度证据缺失、拿不到数字 |
| `drop:stale` | 活跃日期早于时效基准日，或读不到 |
| `drop:irrelevant` | 门槛过了但与需求无关 |

## 缺数据的处理

| 情况 | 处理 |
|---|---|
| 热度字段读不到 | 再核实一次，仍读不到则剔除，记 `drop:traction` |
| 活跃日期读不到 | 同上，记 `drop:stale` |
| 页面无法访问 | 剔除 |

闭源产品经常查不到具体日期，照实剔除；"持续更新中"这类措辞算作没有日期。

## 行数

保留 8 到 20 行。少于 8 行说明覆盖不足，补检索角度再来一轮。多于 20 行说明取舍不够，按关联性和热度收紧。

# 实现方案

候选是机制、算法、模式。star 和热度在这里免用。

## 候选的粒度

一个候选等于一个可命名、可单独取舍的机制。限流的候选是固定窗口、滑动窗口日志、滑动窗口计数、漏桶、令牌桶、并发信号量、集中式配额服务这一层。

粒度判断：两个候选在同样约束下会做出不同取舍，就是两条；同一机制的不同实现合并成一条，实现留给"典型实现"字段。

## 门槛一：生产采用证据

每个方案至少一条可核实的证据，说明它在生产中被使用或被权威文档推荐，带链接。可接受的：

- 主流实现的官方文档或源码位置，例如网关、数据库、标准库里的对应机制。
- 公司工程博客、事故复盘、架构文章里的实际使用记录。
- 标准或规范，例如 RFC、协议文档。
- 论文加上至少一个落地实现。

排除在外的：只在教程、面试题、内容农场文章里出现的方案；只有概念描述、没有任何实现或使用记录的方案。

## 门槛二：证据时效

方案本身按机制保留。时效作用在证据上：至少一条证据在时效基准日之后，说明它当前仍在使用或仍被讨论。

只有多年前文献支撑、近一年找不到任何使用或讨论记录的，记 `drop:legacy`。它若是其他方案的基础概念，在取舍要点里用一句话交代。

## 门槛三：适用条件写得出来

写不出"什么条件下选它"和"什么条件下换掉它"，记 `drop:unclear`，回去补证据或剔除。这一条用来挡只有名字、没有使用条件的候选。

## 判定取值

| 判定 | 含义 |
|---|---|
| `keep` | 三道门槛都过，且与需求相关 |
| `drop:unproven` | 找不到生产采用证据 |
| `drop:legacy` | 近一年无任何使用或讨论记录 |
| `drop:unclear` | 说不清适用条件 |
| `drop:irrelevant` | 门槛过了但与本次约束无关 |

## 关联性在实现方案里的含义

对照复述里的约束那一句：技术栈、规模量级、已有基础设施、部署形态。明显不符合约束的剔除，例如单机进程内方案用在多实例部署上、需要专门协调服务而团队没有这套基础设施。

## 行数

保留 4 到 12 行。行数偏多时先检查是否把同一机制的多个实现拆成了多行。少于 4 行说明机制族没找全，补检索角度再来一轮。

# 两种类型共用的裁量规则

门槛之外的取舍由 agent 判断，依据是 `plan.md` 第一节的复述全文。剔除时记 `drop:irrelevant`。

判断时对照复述里的用途那一句。常见该剔除的情况：

- 名字或标签命中，实际解决的问题不同。
- 属于用户明确排除的范围。
- 同一团队的多个变体，或同一机制的多个实现，只留一条。
- 镜像、fork、教程合集、榜单索引本身。它们是发现渠道。
- 处于长尾且同组已有更有代表性的同类。

## 剔除结果的去向

判定和数量都记在 `screening.jsonl` 里，回复省略。
