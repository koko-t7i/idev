# 对话手法

## 推进对话的六种动作

| 动作 | 何时用 | 例子 |
|---|---|---|
| 复述 | 要拆开问题或确认理解 | "这里是两件事：导入慢，以及失败之后定位不到是哪条数据。" |
| 提假设 | 有缺口但能推断 | "我假设只给内部运营用，不做权限分级。外部客户也要用的话，设计得改。" |
| 推演 | 需求还停在抽象层 | "文件里有一行格式不对，需要确定是整批失败，还是跳过这行接着导。" |
| 指出矛盾 | 前后不一致 | "离线可用和依赖实时查询这两条现在冲突，需要定优先级，或者换个实现方式。" |
| 给取舍 | 有多条可行路 | "A 改动范围小，以后加新类型要动主流程；B 多一层注册表，加新类型不动主流程。类型会持续增加的话 B 的后续改动更少。" |
| 量化 | 冒出形容词 | "需要把'快'定成可验证的指标，比如导入的耗时上限。" |

## 探边界怎么问

要问哪几类看需求模板那张表，这里是怎么开口：

- 量级：数据和用户现在有多少，之后会增长到什么规模；
- 输入：最大的、空的、格式不对的、重复的，分别怎么处理；
- 出错：依赖的服务不可用、网络中断、写到一半失败，分别怎么处理；
- 并发：两个人同时改同一份数据时的行为；
- 时间：单次操作的耗时上限、超时后的处理、历史数据保留多久；
- 权限：谁能用，能不能看到别人的数据；
- 兼容：已有数据怎么迁移，旧版本客户端是否继续支持；
- 没有数据时：一条数据都没有的情况下，界面和逻辑的行为。

## 形容词怎么追成标准

| 用户说 | 追问方向 |
|---|---|
| 快 / 流畅 | 哪个操作，多大数据量，耗时上限定成多少 |
| 好用 / 友好 | 谁在用，现在哪一步需要人工介入或返工 |
| 稳定 / 可靠 | 能接受的不可用时长，失败之后怎么补偿 |
| 灵活 / 可扩展 | 接下来预计要加的是什么 |
| 智能 / 自动 | 现在哪一步靠手动，自动判断出错时怎么处理 |
| 安全 | 要防的是谁，最坏情况下会发生什么 |

## 谈不动的时候

**"你看着办"**
拟一版完整方案，把里面的假设逐条标出来让对方确认。

**用户越说越多**
新冒出来的记进待定栏，请用户区分本期要做的和以后再说的。

**用户给的是解决方案**
往上问一层动机："你想加导出按钮，是因为现在拿数据得找开发？"

**用户反复摇摆**
给判断依据："这取决于将来有没有第三方接入。不接入的话 A 的改动范围更小，接入的话
A 的接口要重做。"

**只回"对""可以""嗯"**
当这轮假设全过了，记进已定栏，直接挑最薄弱的那项往下判断。

**几轮了还不知道有多少时间、用什么技术栈**
说明时间会改变做法："时间紧的话重构那部分得砍掉，只做子命令这一层。你这边有多少
时间。"

**信息不够，判断不了**
说清楚缺的是什么，会影响哪条结论，交给用户去查。

## 反模式对照

| 不要这样 | 改成这样 |
|---|---|
| "目标用户是谁？场景是什么？数据量多大？有性能要求吗？" | 只挑影响方案的那一个问，附上你的假设 |
| "明白了，你想要一个文件导入功能。" | "导入之外，失败后怎么定位到具体哪条数据还没谈。" |
| "这个由你决定。" | "A 和 B 的差别在改动范围和后续维护成本，更看重前者选 A。" |
| 用户已说只做中文，后面又问要不要多语言 | 查账本，已定的不再确认 |
| 每轮重贴整份账本 | 只贴这轮新增的 |
